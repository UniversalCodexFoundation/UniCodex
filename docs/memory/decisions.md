## ADR-001: 依赖方向 — Core 依赖模块，而非模块依赖 Core

**日期**：2026-02-16 · **状态**：已决定

**背景**：
最初考虑让所有 `ucx-*` 模块依赖 `unicodex-core`，由 core 提供公共类型。但这会导致循环依赖问题，并且限制了第三方阅读器只引用部分模块的能力。

**决定**：
`unicodex-core` 仅作为 CLI 入口（bin = `ucx`），**依赖**所有 `ucx-*` 功能模块，而非被依赖。

```
unicodex-core (CLI 入口)
  ├── 依赖 ucx-init
  ├── 依赖 ucx-build
  ├── 依赖 ucx-parse
  ├── 依赖 ucx-verify
  ├── 依赖 ucx-sign
  ├── 依赖 ucx-version
  └── 依赖 ucx-crypto
```

**理由**：
- 第三方阅读器可按需引用：仅 `ucx-parse` + `ucx-verify` + `ucx-crypto` 即可完整支持 UCX 文件读取。
- 功能模块之间可按需互相依赖（如 `ucx-build` 依赖 `ucx-sign` 实现构建时自动签名）。
- 避免不必要的编译依赖。

**影响**：
- 公共类型（如 UCX ID、Manifest 结构）需要放在被多个模块共同依赖的位置。
- 由此衍生出独立的 `ucx-types` 公共类型 crate（当前承载 51 个测试），成为依赖底座。

## ADR-002: ucx-build 与 ucx-parse 分离

**日期**：2026-02-16 · **状态**：已决定

**背景**：
最初 `ucx-build` 同时承担打包和解包职责。但“构建”和“解析”是两个完全不同的操作方向，混在一起会让阅读器被迫编译构建相关代码。

**决定**：
将解析读取功能拆分到独立的 `ucx-parse` 模块：
- `ucx-build`：负责打包构建 UCX 文件（作者 / 出版方使用）。
- `ucx-parse`：负责解析读取 UCX 文件（阅读器 / 验证工具使用）。

**理由**：
- 阅读器只需引用 `ucx-parse`，无需编译构建相关代码（呼应 ADR-001 的按需依赖原则）。
- 职责单一，降低模块复杂度。

**影响**：
- 构建与解析两侧需共享一致的 Manifest / 容器格式约定，约定本身归 `ucx-types` 维护。

## ADR-003: 使用 git2 (libgit2) 而非 Git CLI

**日期**：2026-02-16 · **状态**：已决定

**背景**：
`ucx version auto` 需要检测文件变更来自动生成版本号。有三种方案：
1. 调用系统 `git` 命令；
2. 使用 `git2` crate（libgit2 的 Rust 绑定）；
3. 自实现 diff。

**决定**：
使用 `git2` crate。

**理由**：
- 无需系统安装 Git，降低用户环境依赖。
- 纯 Rust 调用，跨平台行为一致。
- 可作为库嵌入使用。

**影响**：
- 需要为“无 Git 仓库”场景提供回退方案：使用 `.ucx-snapshot.json` 文件哈希快照（详见 ADR-010）。

## ADR-004: 加密在签名之前（Encrypt-then-Sign）

**日期**：2026-02-16 · **状态**：已决定

**背景**：
加密和签名的执行顺序直接影响验证流程能否在不解密的前提下校验完整性。

**决定**：
加密在签名之前执行（Encrypt-then-Sign）。流程：
1. 准备明文文件；
2. 按配置加密 → 得到密文；
3. 对密文计算哈希 → 生成 MANIFEST.MF；
4. 对 MANIFEST.MF 签名。

**理由**：
- 无需解密即可验证文件完整性（签名保护的是密文）。
- 篡改密文 → 签名验证失败；替换密文 → 哈希不匹配。

**影响**：
- 验证路径（ucx-verify）与加密容器格式（UCXE，见 ADR-006）必须协同：签名覆盖密文，AAD 覆盖加密头部。

## ADR-005: 版本语义推荐 卷.章.修订

**日期**：2026-02-16 · **状态**：已决定

**背景**：
小说作品的版本号需求与软件不同。传统 SemVer 的 `MAJOR.MINOR.PATCH` 对小说场景不够直观。

**决定**：
推荐（非强制）`X.Y.Z` = `卷号.章节数.修订号`：
- `X`：当前卷数；
- `Y`：当前卷内最新章节编号；
- `Z`：修正计数，初始值为 0，发布新章节时归零。

作者也可选择 SemVer 或其他自定义语义，UCX 不强制约束。

**理由**：
- 贴合连载小说的心智模型（卷 → 章 → 勘误），读者一眼可读懂作品进度。
- 不强制约束，保留作者自由。

**影响**：
- 版本状态需要跨命令持久化以支撑 `auto/patch/chapter/volume/set` 等子命令（详见 ADR-010）。

## ADR-006: UCXE 二进制格式与 AAD 覆盖范围

**日期**：2026-04（Phase 4 / 安全加固） · **状态**：已决定

**背景**：
加密文件需要一个自描述的二进制容器，既要携带解密所需的算法 / KDF 参数，又要保证头部本身不可被静默篡改。早期设计将头部中的一个字节留作 `Reserved`，未纳入认证范围。

**决定**：
定义 **UCXE** 容器格式：

```
magic "UCXE" | 头部(算法 ID / KDF 参数 / flags 字节) | 密文 | Auth Tag
```

AEAD 的 AAD（附加认证数据）**覆盖完整头部**，且使用**原始 flags 字节**（`raw_flags`，含 reserved bits），而非解析后的标志位。

**理由**：
- 头部参数（算法、KDF 配置、flags）若被篡改将导致按错误参数解密；纳入 AAD 后任何头部改动都会使 Auth Tag 校验失败。
- 使用 `raw_flags` 而非解析后的标志，意味着**即使 reserved bits 翻转也会导致解密失败**，杜绝“保留位”成为静默篡改 / 降级的通道。

**影响**：
- 与 ADR-004 的 Encrypt-then-Sign 协同：外层签名保护密文，UCXE 内层 AAD 保护加密头部。
- 格式向后兼容受限：reserved bits 一旦被赋予含义即改变 AAD 输入，需配合格式版本管理。

**追溯**：
- `af5ad6d` — 将头部 Reserved byte 重定义为 Flags byte。
- `5288720` — AEAD AAD 覆盖 UCXE 头部字节。
- `05dd1f0` — AAD 改用原始 flags 字节（`raw_flags`），覆盖 reserved bits。

## ADR-007: 双层签名失败语义与证书校验

**日期**：2026-03~04（Phase 3 双层签名 / 安全加固） · **状态**：已决定

**背景**：
UCX 采用双层签名：
- **Layer 1**：JAR 式 `SF` / `EC`（逐文件摘要 + 签名文件）；
- **Layer 2**：APK v2 式签名块（Ed25519，覆盖整体容器）。

需要明确：当某一层校验失败时整体判定语义，以及证书可信度如何约束。早期实现存在“一层失败降级为 PARTIAL”的模糊语义，以及外部 `cert.pem` 与签名块内嵌证书不一致、证书过期未校验、私钥文件权限过宽等问题。

**决定**：
1. **任一层失败即判 INVALID**，不降级为 PARTIAL。
2. 强制 `META-INF/certs/*.cert.pem` 与 EC 内嵌证书**逐字节一致**。
3. 验证证书的 `notBefore` / `notAfter` 有效期。
4. 写入私钥文件后**加固文件权限至仅当前用户可读**。

**理由**：
- 签名安全是“全有或全无”：任一层不可信即整体不可信，PARTIAL 会给攻击者降级空间。
- 外部证书与内嵌证书一致性校验，防止用一份“看似可信”的 `cert.pem` 掩盖签名块中的真实签名者。
- 有效期校验防止使用过期 / 未生效证书；私钥权限加固防止本地凭据泄露。

**影响**：
- 验证输出的状态机被简化为 VALID / INVALID（移除签名层面的 PARTIAL 路径）。
- 私钥权限加固在跨平台（Windows / Unix）需各自处理。

**追溯**：
- `e70d28e` — 任一层签名失败均直接 FAIL 而非 PARTIAL [SIG-L1/L2]。
- `9e0bfe0` — 强制 `META-INF/certs/*.cert.pem` 与 EC 内嵌证书一致 [SIG-2]。
- `5c65811` — 校验证书 `notBefore` / `notAfter` 有效期 [SIG-1]。
- `f26bc04` — 写入私钥后加固文件权限 [SIG-5]。

## ADR-008: KDF 选型与口令安全

**日期**：2026-04（Phase 4 加密 / 安全加固） · **状态**：已决定

**背景**：
口令派生密钥（KDF）的强度、口令的规范化、解密失败的反馈方式，以及内存中密钥材料的生命周期，都会影响加密子系统的实际安全性。

**决定**：
1. **KDF**：默认 **Argon2id**，保留 **PBKDF2** 作为兼容回退。
2. passphrase 进入 KDF 前统一执行 **NFC 归一化**。
3. KDF 参数设置**上下限校验**。
4. 公开 decrypt API 在任何失败原因下统一返回 **`decryption failed`** 文案。
5. 使用 **zeroize** 清零密钥材料。

**理由**：
- Argon2id 抗 GPU / ASIC 暴力破解，优于纯迭代型 KDF；PBKDF2 用于与既有 / 受限环境兼容。
- 同一口令在不同输入法 / 平台下 Unicode 形态可能不同，NFC 归一化保证“看起来相同的口令”派生相同密钥。
- 参数上下限校验防止恶意 / 异常参数触发内存或时间型 DoS。
- 统一失败文案避免 padding / 认证 / 参数等差异泄露信息，防止 **decryption oracle**。
- zeroize 缩短密钥材料在内存中的暴露窗口。

**影响**：
- 统一失败文案使调试需依赖内部日志而非公开错误，调试体验与安全性之间作了取舍（倾向安全）。
- NFC 归一化成为口令处理的强制前置步骤，所有口令入口都须遵循。

**追溯**：
- `e985b25` — passphrase 进入 KDF 前统一 NFC 归一化。
- `07da9e2` — 公开 decrypt API 统一返回 `DecryptionFailed`。
- `6ad307a` — 使用 zeroize 清零密钥材料。

## ADR-009: chunked 加密的 nonce 拼接式派生

**日期**：2026-04（Phase 4 加密 / 安全加固） · **状态**：已决定

**背景**：
大文件（> 64 MiB）按 1 MiB 分块加密，每块需要唯一 nonce。早期实现以基础 nonce 与块索引做 **XOR** 派生，存在不同 (base, index) 组合产生相同 nonce 的碰撞风险。AEAD 下 nonce 复用会严重削弱机密性 / 完整性保证。

**决定**：
> 触发阈值：文件 > 64 MiB；分块大小：1 MiB。

将分块 nonce 的派生方式由 **XOR** 改为**拼接式派生**（base 与块索引拼接后派生），保证各块 nonce 唯一、不碰撞。

**理由**：
- XOR 派生不能保证唯一性（不同输入可异或出相同结果）；拼接式派生以确定且单射的方式生成每块 nonce，从结构上消除碰撞。

**影响**：
- chunked 容器的 nonce 派生规则被固定，跨版本解密须保持一致。

**追溯**：
- `9ad7a36` — chunked nonce 派生由 XOR 改为拼接式。

## ADR-010: 版本与文件状态的持久化

**日期**：2026-03（Phase 2 版本管理） · **状态**：已决定

**背景**：
`ucx version` 的子命令（`auto/patch/chapter/volume/set`）需要在多次命令调用之间共享版本状态；`auto` 还需检测文件变更，但不能强制要求用户环境安装 Git（呼应 ADR-003）。

**决定**：
1. **`.ucx-version.json`**：持久化版本状态，跨命令传递当前 卷.章.修订（ADR-005）。
2. **`.ucx-snapshot.json`**：持久化文件哈希快照，作为 **Git 不可用时**的变更检测回退；该文件已加入 `.gitignore`。

**理由**：
- 版本状态需要落盘才能在无状态的 CLI 调用之间延续。
- 快照回退使 `version auto` 在非 Git 环境（如纯目录、解压副本）仍可工作，兼顾 ADR-003 的“无 Git 依赖”目标。
- 快照属本地派生数据，纳入 `.gitignore` 避免污染版本库。

**影响**：
- 两个状态文件成为版本子系统的事实契约，删除或损坏会影响 `auto` 的变更判定。

## ADR-011: 版本号封顶 v0.x.x，直到全功能完成

**日期**：2026-05-30 · **状态**：已决定

**背景**：
项目仍处 alpha 阶段，签名增强（SIG-EXT-001~005）、加密私钥、多语言 SDK、官方服务等关键能力尚未完成。过早跳到 `v1.0.0` 会向用户传递"稳定且功能完整"的错误信号。

**决定**：
在**全部规划功能彻底完成**前，版本号一律保持 `v0.x.x`（按 CLAUDE.md 版本格式带 alpha/beta/rc 后缀）。**禁止**将版本设为 `v1.0.0`。`v1.0.0` 仅作为里程碑 **M6**（全功能完成 + 多语言 SDK + 官方服务就绪，见 [../plan/roadmap.md](../plan/roadmap.md)）的终点标志。

**理由**：
- SemVer 中 `1.0.0` 代表稳定 API 与功能完整承诺；功能未齐时发布 1.0.0 名实不符。
- 保持 `0.x` 明确传达"开发中、API 可能变更"，符合当前 alpha/beta 实际。

**影响**：
- Phase 5（生态建设）完成、SIG-EXT 等遗留增强落地、官方服务可用之前，发布版本只能在 `v0.x.x` 区间递增（如 v0.5.0、v0.6.0…）。
- M6 是唯一允许跨入 `v1.0.0` 的节点。

## ADR-012: 多语言 SDK 版本号方案（标准版本 + 补丁位）

**日期**：2026-05-31 · **状态**：已决定

**背景**：
Phase 5 的多语言 SDK 需要一套清晰的版本号方案，既要表达"该 SDK 支持哪个 UCX 标准"，又要允许 SDK 自身独立迭代修补。

**决定**：
SDK 版本号为 `X.Y.Z`：
- `X.Y`（前两位）= 所支持的 **UCX 标准版本**（major.minor）。**前两位相同 ⇒ 对接同一 UCX 标准、对外 API 相同**。
- `Z`（末位）= SDK 自身补丁号（修 bug、不改对外 API）。

当前所有 SDK 初始版本统一为 **`0.4.0`**（对应 UCX 标准 `0.4.x`）。

**理由**：
- 使用者一眼可知某 SDK 对接哪个 UCX 标准；同 `X.Y` 系列保证对外 API 兼容、可放心升级补丁。
- **旧标准线不废弃**：UCX 标准升级到下一 minor（如 `0.5`）时新增 `0.5.x` SDK 线，而旧 `0.4.x` 线**持续发布补丁**（`0.4.1`、`0.4.2`…），类似 Python 对多个版本系列并行维护。

**影响**：
- 同一 `X.Y` 内只允许**补丁级**变更（不改对外 API）；任何对外 API 变更必须伴随 UCX 标准 minor 升级。
- 与 [ADR-011] 相互独立：ADR-011 约束的是 **UCX 工具链/标准本体**版本（功能完成前封顶 `v0.x.x`）；本 ADR 约束的是 **SDK 版本号与所支持标准的映射**。
- Go / Swift 等以 git tag 表达版本的生态：版本以 tag `v0.4.0` 体现，并在各 SDK README 注明。
- 落地：全部 SDK 的包清单（含 version 字段者）设为 `0.4.0`；各 SDK README 与 `sdk/README.md` 索引含"版本号说明"小节。
