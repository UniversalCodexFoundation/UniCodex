## 3. 已验证的关键问题（High 级）

以下 18 个 High 级发现均已通过对抗性审查确认为真实问题，按优先级分组排列。

### 3.1 [P0] 分块 AEAD 解密未绑定 chunk_count 到 AAD（截断攻击）

**影响范围：11 个 SDK（除 Cangjie 评为 medium 外全部为 high）**

| SDK | 文件 | 行号 | 工作量 |
|-----|------|------|--------|
| Go | `sdk/go/decrypt.go` | 220 | trivial |
| Python | `sdk/python/src/unicodex/crypto.py` | 283 | trivial |
| TypeScript | `sdk/typescript/src/ucxe.ts` | 250 | trivial |
| Dart | `sdk/dart/lib/src/ucxe.dart` | 357 | trivial |
| Java | `sdk/java/src/main/java/org/unicodex/ucx/internal/Decryptor.java` | 259 | small |
| Kotlin | `sdk/kotlin/src/main/kotlin/org/unicodex/ucx/Symmetric.kt` | 96 | small |
| C# | `sdk/csharp/src/Decryptor.cs` | 161 | small |
| C++ | `sdk/cpp/src/ucxe.cpp` | 146 | small |
| Ruby | `sdk/ruby/lib/unicodex/crypto.rb` | 265 | trivial |
| PHP | `sdk/php/src/Crypto/Decryptor.php` | 166 | trivial |
| Swift | `sdk/swift/Sources/Unicodex/Ucxe.swift` | 373 | trivial |
| ArkTS | `sdk/arkts/ucx/src/main/ets/ucx/ucxe.ets` | 373 | trivial |
| Cangjie | `sdk/cangjie/src/ucxe.cj` | 221 | trivial |

**问题本质：**

规范明确要求：`chunk_aad = file_aad || u32_le(chunk_count)`。当前所有 SDK 仅使用 `file_aad`（即 `header(8) || kdf_params || salt`）作为每个分块的 AAD，未将 `chunk_count`（总分块数）追加到 AAD 中。

**攻击场景：**

攻击者可以从加密文件末尾删除任意数量的分块，并将 `chunk_count` 字段改为剩余分块数。由于每个分块的 AEAD 认证不包含总分块数，剩余分块仍然能通过认证，导致解密后产生被截断的明文，且接收方无法检测到数据丢失。

**修复方案（统一模式）：**

```
// 伪代码，适用于所有语言
file_aad = build_aead_aad(header)
chunk_count = read_u32_le(stream)
chunk_aad = file_aad || u32_le(chunk_count)  // <-- 关键修改
for each chunk:
    plaintext = aead_decrypt(key, nonce, ciphertext, chunk_aad)  // 使用 chunk_aad
```

**Rust 参考实现：** `ucx-crypto/src/chunked.rs:135-140` 中的 `build_chunk_aad` 函数正确地追加了 `chunk_count.to_le_bytes()`。

**工作量估算：** 大部分 SDK 仅需 1-3 行代码修改，总计约 2-4 小时。

### 3.2 [P0] 缺少 Zip-Slip 路径遍历验证

**影响范围：12 个 SDK（C# 有部分验证但不完整）**

| SDK | 文件 | 行号 | 确认严重度 | 工作量 |
|-----|------|------|-----------|--------|
| Go | `sdk/go/archive.go` | 180 | high | medium |
| Python | `sdk/python/src/unicodex/archive.py` | 73 | high | medium |
| TypeScript | `sdk/typescript/src/zip.ts` | 50 | high | small |
| Dart | `sdk/dart/lib/src/archive.dart` | 97 | medium* | small |
| Java | `sdk/java/.../ZipReader.java` | 141 | medium* | medium |
| Kotlin | `sdk/kotlin/.../ZipReader.kt` | 69 | medium* | medium |
| C# | `sdk/csharp/src/UcxArchive.cs` | 103 | medium** | small |
| C++ | `sdk/cpp/src/detail.cpp` | 269 | medium | small |
| Ruby | `sdk/ruby/lib/unicodex/zip_reader.rb` | 142 | medium* | small |
| PHP | `sdk/php/src/Internal/ZipReader.php` | 131 | medium* | small |
| Swift | `sdk/swift/.../ZipReader.swift` | 80 | medium | small |
| ArkTS | `sdk/arkts/.../zip.ets` | 197 | medium | small |
| Cangjie | `sdk/cangjie/src/zip.cj` | 208 | medium | small |

> \* 对抗性审查将部分 SDK 从 high 降级为 medium，因为这些 SDK 是只读模式（不会将文件提取到磁盘）
> \** C# 有部分验证（检查 `..` 和 `/`），但缺少反斜杠、驱动器前缀、控制字符、Windows 保留设备名等检查

**问题本质：**

规范 Security Requirements 第 3 条要求所有 SDK 必须实现 `validate_safe_relative_path`，拒绝以下路径：
- `..` 路径段
- 前导 `/` 或 `\`
- Windows 驱动器前缀（如 `C:/`）
- NUL/控制字符（0x00-0x1F）
- Windows 保留设备名（CON, PRN, AUX, NUL, COM1-9, LPT1-9）
- 路径段末尾的点或空格

**修复方案：**

参考 Rust 实现 `ucx-types/src/path_safety.rs::validate_safe_relative_path`，在每个 SDK 的 ZIP 解析阶段为每个条目名调用验证函数。

**工作量估算：** 每个 SDK 需要实现一个约 30-50 行的验证函数，总计约 8-12 小时。

### 3.3 [P0] Kotlin PBKDF2 使用 JDK SecretKeyFactory 产生错误的密钥

**影响范围：仅 Kotlin SDK**

| 字段 | 值 |
|------|-----|
| 文件 | `sdk/kotlin/src/main/kotlin/org/unicodex/ucx/Kdf.kt` |
| 行号 | 100 |
| 严重度 | high |
| 置信度 | 0.95 |
| 工作量 | small |

**问题本质：**

JDK 的 `PBKDF2WithHmacSHA256`（SunJCE provider）将 `char[]` 转换为字节时使用每个字符的低 8 位（ISO-8859-1 风格），**而非 UTF-8 编码**。对于包含非 ASCII 字符（如中文、日文、韩文、emoji、带重音字符）的密码短语，这会产生与参考实现不同的派生密钥。

Java SDK 已识别此问题并切换到 BouncyCastle 的 `PKCS5S2ParametersGenerator`，直接传入 UTF-8 字节。Kotlin SDK 未应用此修复。

**影响：** 使用非 ASCII 密码短语加密的 UCXE 文件在 Kotlin SDK 中**无法解密**（PBKDF2 模式下）。Argon2id 模式不受影响（已正确使用原始 UTF-8 字节）。

**修复方案：**

将 PBKDF2 路径替换为 BouncyCastle 的 `PKCS5S2ParametersGenerator`，直接传入 `pwBytes`（NFC 归一化的 UTF-8 字节数组），与 Java SDK 的 `bcPbkdf2()` 方法完全一致。

## 4. 中等优先级问题（Medium 级）

共 59 个 Medium 级发现，按维度分组归纳。

### 4.1 安全维度（Security）

#### 4.1.1 密钥/密码短语未清零

**影响范围：全部 13 个 SDK**

所有 SDK 在解密完成后均未对派生密钥、密码短语字节、中间密钥材料进行清零。虽然在 GC 语言中无法保证确定性清零，但最佳实践仍建议进行尽力而为（best-effort）的清零操作。

| SDK | 可用清零方法 |
|-----|------------|
| Go | `for i := range key { key[i] = 0 }` + `runtime.KeepAlive` |
| Python | `bytearray` + 循环清零 |
| TypeScript | `key.fill(0)` |
| Dart | `fillRange(0, length, 0)` |
| Java/Kotlin | `Arrays.fill(key, (byte) 0)` |
| C# | `CryptographicOperations.ZeroMemory()` |
| C++ | `sodium_memzero()` 或 `OPENSSL_cleanse()` |
| Ruby | `key.replace("\x00" * key.bytesize)` |
| PHP | `sodium_memzero()` |
| Swift | `withUnsafeMutableBufferPointer` |

**工作量：** 每个 SDK 约 30 分钟，总计约 6-8 小时。

#### 4.1.2 PKCS#7 unpadding 非常量时间

**影响：** Go, Python, TypeScript, Swift, ArkTS, Cangjie

所有这些 SDK 的 PKCS#7 填充验证使用提前返回的比较方式。由于 HMAC 验证在 CBC 解密之前以常量时间完成，此问题**不可被外部攻击者直接利用**。但作为纵深防御，建议改为常量时间实现。

#### 4.1.3 NFC 归一化静默回退

**影响：** Ruby, C++, Cangjie

当 NFC 归一化失败时，Ruby 静默返回原始字符串，C++ 在未编译 utf8proc 时返回恒等变换，Cangjie 仅支持 ASCII/恒等近似。这可能导致非 ASCII 密码短语派生出错误的密钥。

#### 4.1.4 constantTimeEquals 长度不匹配时提前返回

**影响：** Java (`ByteUtil.java:114`), Kotlin (`Symmetric.kt:168`)

与 Cangjie 相同的问题模式。实际风险低（协议标签长度固定），但函数约定声称常量时间而实际未完全满足。

### 4.2 合规维度（Conformance）

#### 4.2.1 Codex 数据模型不完整

**影响：** C++, PHP, Ruby, Cangjie, Python（部分）

多个 SDK 缺少规范定义的嵌套类型（Description, Rights, Dates, Rating, FileVersion），使用原始 `dict`/`map` 或完全省略。

| SDK | 缺失字段/类型 |
|-----|--------------|
| C++ | FileVersion 完全缺失；description/rights/dates/rating 扁平化为顶层字段 |
| PHP | description/rights/dates/rating/fileVersion 仅存在于 raw 数组 |
| Ruby | 同 PHP |
| Cangjie | series/publisher/genre/tags/description/rights/dates/rating/fileVersion 全部缺失 |
| Python | description/rights/dates/rating/fileVersion 为 `dict[str, Any]` 而非类型化 dataclass |

#### 4.2.2 EOCD 验证不充分

**影响：** Python (`signature.py:236`), C++ (`detail.cpp:213`)

使用 `rfind` 或逆向扫描查找 EOCD 签名 `PK\x05\x06` 后未验证 comment_length 字段与文件大小的一致性，可能导致误匹配。

#### 4.2.3 Kotlin PBKDF2 之外的合规问题

- Kotlin `ZipReader` 未检查 mimetype 条目的 STORED 压缩方式（`ZipReader.kt:69`）
- Java `Series.index/total` 使用 `Integer` 而非 `Long`，无法表示完整的 u32 范围（`Codex.java:209`）

### 4.3 稳定性维度（Stability）

#### 4.3.1 整数溢出/截断

| SDK | 文件 | 问题 |
|-----|------|------|
| Java | `ZipReader.java:131` | `centralDirOffset`（long）cast 为 int，>2GB 时溢出 |
| Kotlin | `UcxeCrypto.kt:232` | `ctLen`（u64）`toInt()` 截断 >2GB 密文 |

## 6. 跨 SDK 模式分析

### 6.1 系统性缺陷模式

#### 模式 A：分块 AAD 未绑定 chunk_count

- **影响：** 全部 13 个 SDK
- **根因：** 规范中此要求在 v0.4.x 期间更新，但更新未同步到所有 SDK。Rust 参考实现的 `build_chunk_aad` 函数未被各 SDK 复制。
- **系统性修复：** 创建一个跨 SDK 的修复模板，统一修改模式。建议在 CI 中添加针对 truncation attack 的测试向量。

#### 模式 B：Zip-Slip 路径验证缺失

- **影响：** 12 个 SDK（C# 有部分验证）
- **根因：** `validate_safe_relative_path` 在 Rust `ucx-types` crate 中实现，但未被提取为各 SDK 的必须实现项。
- **系统性修复：** 在 SDK-API.md 中添加 `validate_safe_relative_path` 的伪代码规范，并添加包含恶意路径的测试向量到 conformance test fixtures。

#### 模式 C：密钥材料未清零

- **影响：** 全部 13 个 SDK
- **根因：** GC 语言中密钥清零效果有限，开发者倾向于省略。
- **系统性修复：** 在 SDK-API.md 中明确要求 best-effort 清零，提供各语言的推荐方法。

#### 模式 D：Codex 数据模型不完整

- **影响：** 8+ 个 SDK
- **根因：** 规范中 Codex 的可选字段较多（description, rights, dates, rating, fileVersion, series, publisher 等），各 SDK 实现程度不一。
- **系统性修复：** 在 SDK-API.md 中提供每个可选字段的类型化模型参考，标注哪些字段是必须类型化的。
