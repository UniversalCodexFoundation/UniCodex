## 一、发布工程缺陷（P0，跨组合并）

### [REL-1] release 二进制版本漂移 + 桩命令退出码 0 — Critical
- **来源**：D2 启动即触发
- **现象**：`target/release/ucx.exe` 在 Phase 4 完结时仍是 0.3.0-alpha.1（Phase 3 桩版），Cargo workspace 是 0.4.0-alpha.1；桩命令 `encrypt`/`decrypt` 输出 `not yet implemented` 并**退出码 0**
- **危害**：CI 流水线 `ucx encrypt --all && upload.sh` 会把**全书明文**当作已加密并上传到公开 CDN，触发**静默灾难性失败**
- **阻塞发布**：✅ **BLOCKER**
- **修复**：
  1. 发布 CI 硬校验 `$(./target/release/ucx --version) == ucx $(cargo pkgid | cut -d'#' -f2)`
  2. 所有桩命令改为 exit code `2` + stderr 输出
  3. `git tag` 前阻止 workspace 与 binary 版本不一致

## 二、密码学规范级隐患（P0）

### [CRYPTO-1] Chunked nonce 用 XOR 合成会 GCM 碰撞 — Critical
- **来源**：D2，`04-crypto-spec.md §8.3`
- **问题**：`nonce = base_nonce XOR uint96_le(chunk_index)` 存在可预测的 nonce 碰撞
- **GCM 下果**：认证密钥 H 可恢复 → 伪造任意密文 + 解密全体历史
- **阻塞发布**：✅ **BLOCKER**
- **修复**：改为拼接式 `nonce = base_nonce_96 || uint32_be(chunk_index)`，或采纳 RFC 8446 的 per-record nonce

### [CRYPTO-2] UCXE 头部未纳入 AEAD 的 AAD — Critical
- **来源**：D2，`04-crypto-spec.md §4.1`
- **问题**：Magic / format version / algo ID / KDF ID / flags 未作为 AAD 参与认证
- **攻击**：无签名保护的孤立 UCXE 可被跨头部降级篡改（把 AES-GCM 标成 AES-CBC 触发不同 code path）
- **阻塞发布**：✅ **BLOCKER**
- **修复**：`associated_data = UCXE 头部全部字节 || KDF 参数 || salt`

### [CRYPTO-3] AES-CBC HMAC 覆盖范围不完整 — High
- **来源**：D2，`04-crypto-spec.md §4.3`
- **问题**：HMAC-SHA256 只覆盖 `IV || ciphertext`，未覆盖算法/KDF ID/flags
- **阻塞发布**：⚠️ 强烈建议 blocker
- **修复**：同 CRYPTO-2

### [CRYPTO-4] KDF 参数解码下限未定义 — High
- **问题**：攻击者可用 Argon2 iterations=1 / memory=8KB 生成加密文件分发，接收方若不拒绝→暴力瞬破
- **阻塞发布**：⚠️ 强烈建议 blocker
- **修复**：规范钦定最小参数；解码器必须拒绝低于下限

## 三、签名/身份 High 级漏洞

### [SIG-1] 证书有效期在 verify 时未校验 — High
- **来源**：D4 初测 + 0.4.0 复测
- **现象**：`cert create --days 1` 后手动把 `notAfter` 改到过去，sign 成功、`verify` 返回 **VERIFIED**，无过期告警
- **违反**：`08-keys-identity.md §5.2/§5.3`
- **阻塞发布**：✅ **BLOCKER**（签名体系可信根被击穿）
- **修复**：`verify` pipeline 必须校验 Layer-1 证书 `notBefore ≤ now ≤ notAfter`，不通过则 Status=FAIL

### [SIG-2] META-INF/certs/*.cert.pem 与 EC 内嵌 cert 不一致不告警 — High
- **来源**：D4 初测 + 0.4.0 复测
- **现象**：替换 cert.pem 为 AuthorA 的证书但 EC 内嵌 AuthorB 的 cert，verify 展示 Subject=AuthorB 但仍显示 SIGNER_ID=AUTHOR
- **危害**：钓鱼攻击 — 冒充某作者身份
- **阻塞发布**：✅ **BLOCKER**
- **修复**：verify 阶段强制 `cert.pem ≡ EC 内嵌 cert`，不一致即 FAIL

## 四、鲁棒性 High 级漏洞

### [ROB-1] UCX-Version 字段值被静默接受 — High
- **来源**：D3 F-01
- **现象**：`UCX-Version: 99.0` 写入 MANIFEST.MF 后 `verify` 仍通过
- **违反**：`07-versioning.md §2.5` 兼容性矩阵
- **阻塞发布**：✅ **BLOCKER**（未来版本发布时解析器无法区分旧/新）
- **修复**：verify/info 遇到 major 超限 Version 必须拒绝或强 WARN

### [ROB-2] ZIP 前置字节被接受（Polyglot） — High
- **来源**：D3 F-02
- **现象**：`cat a.ucx a.ucx > doubled.ucx` 后 `info`/`verify` 均成功（ZIP 解析器以最后一个 EOCD 为准）
- **危害**：签名绕过 / 恶意前缀夹带 / polyglot 文件攻击
- **阻塞发布**：✅ **BLOCKER**
- **修复**：parser 拒绝任何 EOCD 之前的 non-zero 字节；或校验 ZIP 起始偏移 = 0

## 十、测试方法自评

### 优点
- 4 代理并行覆盖 4 个维度，独立视角无污染
- D3/D4 严格遵守"只读 docs、禁读 .rs"约束，输出质量高
- 发现了真实用户会踩的**版本漂移灾难**（启动时即触发）

### 不足
- D1 原代理未落盘报告，被 shutdown 后由 lead 接手整合，证据密度略低
- D2 原代理第一轮被桩二进制阻塞 → 重跑后仍未落盘，被 shutdown
- Layer 2 签名深度 fuzz 不充分（Python zipfile 重打包破坏 magic，见 D4-L5）

### 改进建议（下一期测试）
- Agent prompt 里加 "每跑一组立刻 append 到报告文件" 强制循环
- 增加一个专门 fuzz Layer 2 签名的代理，用 Rust/C 自建 zip writer 保持 magic

## 十一、结论

Phase 4 核心加密能力在 0.4.0-alpha.1 上**主路径可用**（AES-GCM/ChaCha20 direct key + passphrase 三套算法 roundtrip 正常），但在以下三个维度存在**阻塞发布**的风险：

1. **发布工程**：版本漂移 + 桩命令静默成功，能把明文上传合法化
2. **密码学规范**：chunked nonce XOR 碰撞、AEAD 不覆盖头部、AES-CBC HMAC 范围不足，均为真实攻击面
3. **签名身份**：证书过期不检查 + cert.pem 与 EC 内嵌 cert 不一致不告警，击穿可信根

**建议**：当前版本不宜外发 beta，需先完成"必须修复"7 项，重跑 D2/D4 回归后再进入 v0.4.0-beta.1。
