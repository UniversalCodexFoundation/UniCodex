## 一、设计标准合规性问题

> 以下问题为实际实现与 `docs/00-09` 设计标准文档之间的不一致。

### P-001 [严重] MANIFEST.MF 中 BLAKE3-Digest 使用 Hex 编码，规范要求 Base64 ✅ 已修复

**涉及标准**：`01-file-structure.md` §3.2

**规范原文**：
> `{Algorithm}-Digest` | 条目 | 是 | **Base64 编码的哈希值**

**实际行为**：
```
BLAKE3-Digest: 5375370778d8aae45132febfce33cd417a807ba195d49e400bfff4f7c376cde9
```

Digest 为 64 个十六进制字符（Hex 编码，256 bit = 32 bytes），而非 Base64。Base64 编码 32 字节应产生约 44 个字符（含 padding）。

**影响**：与规范定义不一致。第三方实现若按规范使用 Base64 解码将导致兼容性问题。

**建议**：统一为一种编码。若选择保留 Hex，则需同步更新规范文档；若遵循规范，则修改代码输出 Base64。推荐参考 JAR 规范使用 Base64，与规范保持一致。

### P-002 [中等] MANIFEST.MF 中 Created-By 名称与规范不一致 📋 已纳入后续计划

**涉及标准**：`01-file-structure.md` §3.2 示例、`07-versioning.md` §5.2

**规范示例**：
> `Created-By: unicodex-cli 0.1.0`

**实际输出**：
```

```

规范使用 `unicodex-cli`，实际使用 `unicodex`。虽然规范说明 `Created-By` 字段非必需，但作为工具标识应在规范与实现之间保持一致。

**建议**：统一命名。推荐使用 `unicodex-core`（与 crate 名一致）或 `ucx`（与 CLI 命令名一致），同时更新规范文档。

*开发者批注：这是标准文档的设计失误，应为Unicodex，需要修复规范文档*

### P-003 [中等] ucx init 未创建 Git 仓库和 .gitignore 文件

**涉及标准**：`07-versioning.md` §3.4.5、`00-overview.md` §7.1

**规范设计**：
- 版本管理基于 `git2`（libgit2），`ucx version auto` 依赖 Git 仓库
- ADR-003 明确选用 git2 而非 Git CLI

**实际行为**：`ucx init` 创建项目后：
- 无 `.git/` 目录（未初始化 Git 仓库）
- 无 `.gitignore` 文件

**影响**：
1. 后续 `ucx version auto` 将无法工作（依赖 Git 仓库）
2. `dist/` 目录（构建输出）无 `.gitignore` 保护，可能被误提交
3. 用户需额外手动执行 `git init`

**建议**：
- `ucx init` 应自动调用 `git2::Repository::init()` 初始化 Git 仓库
- 自动生成 `.gitignore`，至少包含 `dist/` 和常见临时文件
- 可提供 `--no-git` 选项跳过 Git 初始化

### P-004 [中等] ucx init 创建过多冗余目录

**涉及标准**：`02-metadata-spec.md` §5.1

**规范定义**的推荐项目结构包含 `assets/`、`extras/`、`dist/`，但实际上：
- `assets/` — 空目录，仅在有封面/插图时才需要
- `extras/` — 空目录，仅作草稿存放，很多项目永远不会用到
- `dist/` — 空目录，由 `ucx build` 自动创建即可

**实际行为**：`ucx init` 总是创建全部 4 个子目录（`content/`、`assets/`、`extras/`、`dist/`）

**建议**：
- 最简初始化只创建 `content/`（必需目录）
- `assets/`、`extras/` 可在用户实际需要时创建，或通过 `--template` 选项加入
- `dist/` 应由 `ucx build` 在构建时按需自动创建
- 可提供 `--full` 选项创建完整结构
- 可提供 `--template` 选项指定模板结构

### P-005 [中等] struct.json 的 `file` 与 `children` 互斥规则未校验 ✅ 已修复

**涉及标准**：`01-file-structure.md` §4.1

**规范原文**：
> 有 `file` → 叶子节点，**不可有 `children`**
> 有 `children` → 容器节点，**不可有 `file`**
> 两者必须二选一

**实际行为**：当 struct.json 中一个节点同时包含 `file` 和 `children` 时，`ucx build` 成功构建，**无任何报错或警告**。

**测试用例**：
```json
{
  "structure": [{
    "title": "both_present",
    "file": "chapter-001.md",
    "children": [{"title": "sub", "file": "chapter-001.md"}]
  }]
}
```

**影响**：违反规范约束的文件能正常构建，可能导致下游解析器行为不确定。

**建议**：`ucx build` 应在读取 struct.json 后校验此互斥约束，遇到违规时报错终止。

### P-006 [低] struct.json 引用不存在的文件时 build 不报错 ✅ 已修复

**涉及标准**：`01-file-structure.md` §4.1

**实际行为**：当 struct.json 引用了 `nonexistent.md` 等不存在的文件时，`ucx build` 仍然成功（exit code 0）。构建的 UCX 文件中不包含这些文件，但 struct.json 的引用指向了空目标。

**影响**：用户可能不知道自己的章节文件缺失，直到阅读器打开时才发现问题。

**建议**：`ucx build` 应扫描 struct.json 中所有 `file` 引用，验证对应文件是否存在于 `content/` 目录下。缺失时应输出警告或报错。

*开发者批注：推荐增加 `ucx check` 命令，提供检查功能，同时在构建阶段也进行检查。*

### P-007 [低] codex.json 中缺少 `dates` 字段

**涉及标准**：`02-metadata-spec.md` §2.2

**规范定义**：codex.json 包含可选的 `dates` 对象：
```json
"dates": {
  "created": "2025-01-01",
  "published": "2025-06-01",
  "modified": "2025-12-01"
}
```

**实际行为**：
- `ucx init` 生成的 `unicodex.toml` 无 `[dates]` 段
- `ucx build` 产生的 codex.json 无 `dates` 字段
- 即使是 `created` 日期（可在 init 时自动设置），也未自动填充

**建议**：`ucx init` 应在 `unicodex.toml` 中自动填入 `dates.created = "当前日期"`。`ucx build` 应在 codex.json 中自动更新 `dates.modified`。

### P-008 [低] codex.json 缺少 `file_version` 字段

**涉及标准**：`07-versioning.md` §3.2

**规范定义**：codex.json 应包含 `file_version` 对象：
```json
"file_version": {
  "version": "1.1.0",
  "revision": 1,
  "released_at": "2025-12-01T00:00:00Z"
```

**实际行为**：构建产生的 codex.json 无 `file_version` 字段。

**建议**：虽然版本管理模块（ucx-version）尚未实现，但至少应在 init 时设置初始版本 `"0.0.0"` 或 `"1.0.0"`，并在 build 时写入 `released_at`。

### P-009 [信息] unicodex.toml 模板不够完整

**涉及标准**：`02-metadata-spec.md` §5.2

**规范定义的完整 unicodex.toml** 包含大量可选段（`[series]`、`[description]`、`[rights]`、`[cover]`、`[rating]`、`[dates]`、`[comments]`、`[extensions]`、`[chain]`、`[signing]` 等）。

**实际行为**：`ucx init` 生成的模板仅包含最小必需段：
```toml
[project]
version = "1.0"
[identifier]
ucx_id = "..."
[title]
main = "..."
[[creators]]
name = "..."
role = "author"
[book]
language = "zh-CN"
[build]
output_dir = "dist"
```

**建议**：生成的模板应包含被注释掉的可选段示例，帮助用户了解所有可用配置项。例如：
```toml
# [description]
# short = "一句话简介"
# long = "详细简介"

# [rights]
# statement = "版权所有 (C) 2026 作者名"
# license = "All-Rights-Reserved"
```

## 二、用户体验问题

### UX-001 [中等] `ucx init` 接受空字符串的 name 和 author ✅ 已修复

**实际行为**：`ucx init -n "" -a ""` 成功创建项目，生成的 unicodex.toml 中 `main = ""` 和 `name = ""`。

**影响**：空标题和空作者名不应是有效值。规范要求 `title.main` 和 `creators[].name` 为必需字段。

**建议**：对 `--name` 和 `--author` 参数进行非空验证。空字符串应报错提示。

---

### UX-002 [中等] `ucx init` 不验证 BCP 47 语言标签

**实际行为**：`ucx init -l "not-a-valid-language-tag-at-all-1234567890"` 成功创建项目，无任何警告。

**影响**：无效的语言标签会导致不规范的 codex.json，影响国际化处理和阅读器的语言识别。

**建议**：对 `--language` 参数进行基本的 BCP 47 格式验证。至少校验格式（`xx` 或 `xx-XX`），或使用 `icu` crate（项目已引入）进行标准校验。

---

### UX-003 [中等] `ucx init` 默认在当前目录操作，无确认提示

**实际行为**：`ucx init`（无参数）直接在当前工作目录创建项目文件，不做任何确认。

**影响**：用户在错误的目录下执行 `ucx init` 可能意外创建 `unicodex.toml`、`content/`、`assets/` 等文件。虽然已有幂等性保护（已存在项目时报错），但**首次执行**时无任何防护。

**建议**：
- 当 `PATH` 参数为默认值 `.`（当前目录）且当前目录非空时，提示用户确认
- 或在初始化成功后显示清晰的提示，告知用户在哪个目录创建了什么文件

---

### UX-004 [低] INFO 日志在正常操作时过于冗长 ✅ 已修复

**实际行为**：每次执行命令都输出大量带时间戳的 `INFO` 级别日志：
```
2026-02-16T09:46:07.853961Z INFO ucx_init: Created project root directory ...
2026-02-16T09:46:07.854632Z INFO ucx_init: Created subdirectory ...
...
```

**影响**：对普通用户而言信息过多，降低可读性。CLI 工具应默认简洁输出，详细信息通过 `--verbose` / `-v` 选项启用。

**建议**：
- 默认日志级别设为 `WARN`（仅显示警告和错误）
- 正常操作只输出最终结果（如 `UCX project initialized: "xxx" at /path`）
- 提供 `--verbose` / `-v` 标志显示 INFO 级别详情
- 提供 `--quiet` / `-q` 标志静默模式

---

### UX-005 [低] 未实现命令的错误提示不友好 ✅ 已修复

**实际行为**：
- `ucx unpack some.ucx` → `error: unexpected argument 'some.ucx' found`（误导性错误信息）
- `ucx version` → `ucx version: not yet implemented (planned for Phase 2)`（良好）
- `ucx sign some.ucx` → `error: unexpected argument 'some.ucx' found`

**影响**：`unpack`/`sign`/`encrypt`/`decrypt` 命令虽然已在 CLI 中注册，但参数配置缺失，导致用户传入必要参数时获得"未知参数"错误，而非"功能未实现"提示。

**建议**：所有未实现命令应统一显示类似 `ucx version` 的友好提示：`ucx unpack: not yet implemented (planned for Phase 2)`，而非暴露 clap 的参数解析错误。

### UX-006 [低] ucx info 缺少一些有用信息

**实际行为**：`ucx info` 输出了标题、作者、语言、结构、清单等基本信息，但缺少：

- UCX 规范版本
- 构建工具版本（Created-By）
- 章节总数统计

**建议**：丰富 `ucx info` 输出，展示更多 codex.json 中的字段。

### UX-007 [信息] `ucx build` 覆盖已有文件无警告

**实际行为**：重复执行 `ucx build` 直接覆盖已有的 `.ucx` 文件，无任何提示。

## 三、安全与健壮性问题

### SEC-001 [严重] 路径遍历攻击未防护 ✅ 已修复

**实际行为**：`ucx init "/tmp/ucx-test/test9/../../../etc/evil"` 成功执行，在路径遍历后的实际目标位置创建了项目。

**测试结果**：路径 `/tmp/ucx-test/test9/../../../etc/evil` 被解析并在 `C:/Users/MoYeR/AppData/Local/Temp/etc/evil` 创建了文件。虽然在 Windows 上未造成实际危害（因为路径解析限制），但在 Linux 系统上可能在敏感目录创建文件。

**影响**：恶意路径参数可能导致在意外位置创建文件。

**建议**：
- 对输入路径进行规范化（canonicalize）处理
- 检测并拒绝包含 `..` 的路径组件
- 至少输出警告：`Warning: resolved path is /etc/evil, continue? (y/N)`

---

### SEC-002 [中等] 超长输入未限制

**实际行为**：10000 字符长的作品名被完全接受并写入 unicodex.toml 和 codex.json。

**影响**：
1. 极长的标题可能在某些文件系统上导致问题（当用作输出文件名时）
2. 可能导致 UI 渲染异常
3. 消耗不必要的存储空间

**建议**：对 `--name`、`--author` 等参数设置合理的长度上限（如 500 字符），超出时报错。

*开发者批注：保留对超长标题和作者名的兼容性，如设置--name-long --author-long 参数来保持兼容，这需要在标准文件中进行补充，维护两个参数记录是否启用超长名称，启用后则不对其进行限制，但是在一些处理时进行强制截取或可设置短别名。这是为了兼容某些可能存在的名称非常长的作者和书名，同时避免因名称过长而导致的程序问题。*
---

### SEC-003 [低] 注入攻击虽未造成实际危害，但应增加输入验证 ✅ 已修复

**实际行为**：`ucx init -n '"; rm -rf / #' -a "'; DROP TABLE users; --"` 成功创建项目。TOML 序列化正确处理了特殊字符（使用单引号包裹），JSON 序列化也正确转义。

**评价**：Rust 的 TOML/JSON 序列化库天然防御了注入攻击，这是正面的。但仍建议对用户输入进行基本的合理性校验（如禁止控制字符 `\x00-\x1F`）。

---

### SEC-004 [信息] 构建产物完整性依赖单一哈希层

**现状分析**：当前 UCX 文件的完整性保护仅依靠 MANIFEST.MF 中的 BLAKE3 哈希。签名机制（Layer 1 和 Layer 2）尚未实现。

**影响**：
1. MANIFEST.MF 本身可被篡改（因为无签名保护）
2. 攻击者可同时修改文件内容和对应的哈希值，从而绕过 `ucx verify`
3. 完整的安全需要签名机制的实现（Phase 2-3）

**验证测试**：`ucx verify` 能正确检测到内容篡改（修改章节内容但不修改 MANIFEST.MF 时报错），这是正确的。但若攻击者同时修改 MANIFEST.MF 和内容，当前无法检测。

**建议**：这是已知的 Phase 1 限制，应在 Phase 2（ucx-sign）中解决。但建议在 `ucx verify` 的输出中明确提示：`Warning: no signatures found — integrity check only validates against MANIFEST.MF hashes`。
